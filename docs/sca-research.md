# SCA research and proposed scope

Research date: September 30, 2026. This design research preceded implementation and is based on primary project documentation, public research, and inspection of the repository at that time. Project capabilities below are upstream claims unless explicitly described as paper-reported measurements. The research phase did not run a comparative benchmark or dependency scan. Subsequent implementation checks are recorded in [implementation QA](sca-qa.md).

The follow-on [MVP implementation plan](sca-mvp-plan.md) specifies the initial scope, SDK entry point, OSV adapter, developer workflow, and evaluation gates.

**Recommendation.** Use existing tools to identify affected dependencies, then use Codex to explain their application relevance with inspectable evidence and help with an update. Preserve the package/advisory match even when application relevance is unresolved. Start with known dependency vulnerabilities; treat license compliance and novel malicious-package detection as separate expansions.

**What the current tools already do.** There is no single demonstrated winner across all ecosystems and tasks. A modern comparison needs to include inventory, application context, upgrades, and ongoing reassessment.

OSV's documented call analysis is Go-based plus experimental Rust analysis; broad package extraction does not imply broad function-level reachability. Its guided remediation is also experimental. See [call-analysis coverage](https://google.github.io/osv-scanner/usage/scan-source#scanning-with-call-analysis) and [guided remediation](https://google.github.io/osv-scanner/experimental/guided-remediation/). A release should publish a capability matrix for each ecosystem rather than a single supported-language badge.

**The techniques solve different questions.** The following distinctions should be visible in both the implementation and evaluation.

| Technique                                     | What it establishes                                                                                  | What remains uncertain                                                                            |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Manifest and lockfile parsing                 | Declared dependencies and, for resolved lockfiles, selected versions.                                | Installed or deployed contents may differ; optional dependencies and build profiles matter.       |
| Installed-package or artifact inspection      | Components present in a particular environment, image, archive, or binary.                           | Origin and dependency edges may be incomplete; a source inventory may describe a different build. |
| Ecosystem/version/advisory matching           | A component version falls within a recorded affected range.                                          | Application impact, advisory completeness, and vendor backports.                                  |
| Code fingerprints, symbol or patch comparison | Vendored, repackaged, or compiled code resembles an identified component or affected implementation. | Precision varies with transformations and available metadata.                                     |
| Import/package-use analysis                   | The application uses some part of a dependency.                                                      | Whether it uses the affected function or behavior.                                                |
| Static call graphs and dataflow               | A possible path connects application code to relevant dependency behavior.                           | Dynamic dispatch, reflection, incomplete builds, and configuration assumptions.                   |
| Ordinary test/runtime observations            | A path or component executed under the observed workload.                                            | Unobserved paths are not proven absent.                                                           |
| Contextual assessment                         | Available code and configuration evidence supports or weakens the advisory's applicability.          | Missing deployment facts or uncertain analysis must remain explicit.                              |
| Dependency resolution and update checks       | A proposed update can resolve and pass specified compatibility checks.                               | Passing tests only supports the behavior those checks cover.                                      |

OSV recommends resolved lockfiles rather than guessing installed versions from manifest ranges. Trivy explains how distribution backports make naive upstream-version matching wrong. Go's analyzer explicitly documents both conservative false positives and reflection/unsafe-related blind spots. These are concrete coverage issues an integration must retain, rather than flattening every result into a yes/no answer. Sources: [OSV inputs](https://google.github.io/osv-scanner/supported-languages-and-lockfiles/), [Trivy matching](https://trivy.dev/docs/latest/guide/scanner/vulnerability/), [govulncheck limitations](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck).

**LLM-based work exists, but it is not one uniform category.** The most relevant systems combine structured evidence with model reasoning. A project README establishes that an implementation exists; it does not establish production accuracy.

| Work                                                                                            | What the LLM contributes                                                                                               | Evidence and limits                                                                                                                                                                                                                                             |
| ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [NVIDIA vulnerability-analysis](https://github.com/NVIDIA-AI-Blueprints/vulnerability-analysis) | Combines vulnerability information and container/context evidence into applicability assessments and VEX-style output. | Actual public reference implementation. Evaluate the current pipeline independently; historical results do not automatically characterize a revised architecture.                                                                                               |
| [AppThreat Chennai](https://github.com/AppThreat/chennai)                                       | Lets an agent query static-analysis graphs, inspect source, and explain evidence.                                      | Actual open-source hybrid system; useful evidence-navigation design. No independently verified SCA accuracy result found in this review.                                                                                                                        |
| [RAPTOR SCA](https://github.com/gadievron/raptor/blob/main/docs/sca.md)                         | Optional triage and upgrade-impact review above mechanical SCA results.                                                | Its documented reachability decisions are mechanical, not LLM verdicts. Review this SCA module separately from the project's other capabilities.                                                                                                                |
| [CognixShield, August 2026 revision](https://arxiv.org/abs/2506.17798v3)                        | Structured code fragmentation and retrieval support vulnerability-specific API-use reasoning.                          | Formerly titled SAVANT. The current paper reports 84% precision, 95% recall, and 89% F1 on 57 Java applications. These are authors' results on their task, not an end-to-end multi-language SCA guarantee. A maintained public implementation was not verified. |
| [SCA-Agent, September 2026 preprint](https://arxiv.org/html/2609.18391v1)                       | Reconstructs component provenance through code, build, release, deployment, and runtime stages.                        | Reports 96.69% F1 for component-level vulnerability exposure on its dataset. The paper explicitly distinguishes that task from vulnerable-code reachability. A maintained turnkey open-source package was not verified.                                         |

These results should not be ranked together: component detection, application applicability, and vulnerable API usage have different labels and denominators. My inference is that Codex should first contribute contextual assessment and understandable remediation, while existing tools own the initial package/version facts. Structured retrieval and language-specific analysis should be evaluated as additions to Codex's existing static triage.

**Detection scope.** The first release should answer a sequence of concrete questions:

1. What exact direct and transitive components are resolved, where are they recorded, and which build/runtime scope is known?
2. Which versioned advisories match those components, with aliases, affected ranges, known fixes, and source timestamps preserved?
3. What evidence establishes application relevance, and what additional fact would resolve an unknown assessment?
4. Which direct dependency or constraint needs to change to obtain an appropriate fixed transitive version?
5. What changed after the update, and which compatibility checks passed?

Track three independent records: **component/advisory match**, **application assessment**, and **remediation state**. An affected package can remain present while application relevance is unknown or ruled out for a specified scope. An update can be available but not yet tested. A reviewed conclusion should name its repository revision or artifact, build profile, and applicable configuration.

Suggested initial metadata includes ecosystem, package name, resolved version, package URL when available, occurrence/lockfile, direct/transitive relationships, scope, advisory ID/aliases, match method, affected/fixed ranges, scanner version, and advisory timestamp. Package identity and advisory data should follow existing standards where possible: [Package URL](https://github.com/package-url/purl-spec) and [OSV](https://ossf.github.io/osv-schema/).

Prioritization should keep severity, application evidence, and broader exploitation signals distinguishable. EPSS estimates observed exploitation activity over the next 30 days; it is not an application-specific probability or a complete risk score. Avoid an unexplained multiplication of these signals into a supposedly precise number. [FIRST guidance](https://www.first.org/epss/using-epss)

Known malicious releases are a related but distinct feed: [OpenSSF Malicious Packages](https://github.com/ossf/malicious-packages) publishes OSV-format reports. New malicious-package discovery requires different evidence and evaluation. A dependency used during installation or builds can matter even if absent from runtime imports. License policy, provenance, and maintenance health should likewise be separate result categories; [Scorecard](https://github.com/ossf/scorecard) offers security-practice heuristics, not proof that a package is vulnerable or malicious.

**Success must be measured in layers.** Fewer alerts alone is not a useful objective: dropping every alert would optimize that metric.

| Layer                  | Main measurements                                                                                                         | Essential slices                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Inventory              | Exact component/version precision and recall; dependency-edge correctness; explicit unresolved/unsupported fraction.      | Direct/transitive; runtime/build/test; ecosystem; source versus shipped artifact.              |
| Advisory matching      | Precision/recall against adjudicated versioned references; alias handling; freshness lag.                                 | Version boundaries, prereleases, backports, withdrawals, missing metadata.                     |
| Application assessment | Affected-case recall; incorrect dismissals; correctness of not-affected decisions; reason macro-F1; evidence correctness. | Language, dynamic features, configuration, missing information, positive and negative classes. |
| Uncertainty            | Fraction assessed conclusively, accuracy among conclusive decisions, and unknown reasons.                                 | Unknowns stay in the denominator and visible in reports.                                       |
| Remediation            | Correctly resolved target versions; residual/new advisory matches; passing builds/tests; reviewer acceptance.             | Direct/transitive, patch/major, source migration, unavailable fix.                             |
| Developer value        | Review time per alert, time to accepted update, overrides/reopens, actionable new alerts per PR.                          | First run versus repeat run; small project versus monorepo.                                    |
| Operations             | p50/p95 latency, cost per assessment, tool/model failures, reproducibility.                                               | Cold/cached runs; ecosystem; repository size.                                                  |

Define **false suppression** as a genuinely affected case receiving a not-affected conclusion. Report both the missed fraction of affected cases and the error fraction among not-affected decisions. Unknowns are neither successful dismissals nor confirmed positives. Report selective performance as more or fewer cases receive conclusive judgments.

Useful external datasets cover different layers:

- [VEX-Bench](https://arxiv.org/html/2609.08040v1) is a directly relevant September 2026 applicability benchmark: 75 expert-labeled cases across Java, Go, and Python. It reports roughly 80% best status F1 and lower explanation-label performance. Its small, imbalanced sample and binary labels make it a diagnostic set rather than a sole release gate. [Public code/data](https://github.com/steven1518/vex-bench)
- [A Ground-Truth-Based Evaluation of Vulnerability Detection Across Multiple Ecosystems](https://arxiv.org/html/2604.21111v1) evaluates advisory resolution using exact package/version inputs. Because its reference is OSV-derived, OSV's agreement is perfect by construction. It does not measure inventory discovery; reference disagreements need independent adjudication.
- [BUMP](https://github.com/chains-project/bump) supplies reproducible breaking dependency updates, useful for compatibility work. Its 571 Maven updates across 153 projects do not establish security-detection accuracy. [Paper](https://arxiv.org/abs/2401.09906)

Build our own adjudicated set alongside these resources. Pin source revisions, resolved dependency inputs, artifact/platform context, advisory snapshots, and tool versions. Include direct and transitive dependencies, optional features, aliases, patched distributions, generated/vendored code, missing evidence, and ordinary configuration changes. Use independently reviewed labels and retain disagreement as unknown when the facts are insufficient.

Separate development and held-out cases by repository family and advisory/package family, including aliases and adjacent versions. Add later-in-time cases. Keep evaluator answers and future fixing-PR context out of the evidence available to evaluated systems. Repeat model runs, report variation and confidence intervals, and avoid counting correlated cases as independent samples.

Compare three configurations on the same inventory and advisory inputs: scanner alone, scanner plus conventional static analysis, and scanner plus Codex assessment. An additional comparison should test whether structured analysis improves Codex's assessment. Run upgrade evaluation separately. This isolates where the LLM helps and whether it introduces unsupported dismissals.

Proposed initial release criteria are behavioral: supported fixtures have no silent omissions; every conclusion has inspectable evidence; unresolved analysis remains visible; and an update is called verified only when fresh resolution and the prescribed checks succeed. Begin with review assistance. Any later automatic dismissal needs a separately measured error bound and sufficient independent examples. Set cost and latency targets from representative pilot workloads instead of choosing numbers without measurements.

**Developer experience.** The central unit should be a decision the developer can act on, with access to the underlying component occurrences.

| Moment             | Expected experience                                                                                                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First local run    | Show discovered ecosystems, covered inputs, dependency matches, known fixes, and incomplete areas promptly. Deeper assessments can arrive afterward.                                                                                        |
| Pull request       | Show newly introduced or materially changed dependency exposure relative to the base revision. Keep existing debt accessible without repeating it as new. Code/configuration changes can alter relevance even when a lockfile is unchanged. |
| Inspect a result   | Explain why the dependency exists, what advisory matched, what evidence supports applicability, what remains unknown, and the proposed action.                                                                                              |
| Fix                | Offer a reviewable update to the appropriate direct dependency, manifests, lockfiles, and necessary source usage. Report compatibility checks and remaining advisories.                                                                     |
| Ongoing monitoring | Rematch stored inventories when advisory data changes. Reassess when dependency, code, build, configuration, or advisory evidence invalidates the prior conclusion.                                                                         |
| Accept or defer    | Store the decision with its scope, reason, owner, and conditions for reassessment. Distinguish a human risk decision from a technical not-affected conclusion.                                                                              |

A synthetic review card might say:

> **Update `sample-client` to resolve an affected transitive dependency.**
> `sample-parser@2.1.0` is introduced by `sample-client@4.0.0` in the service lockfile.
> The package version matches the supplied advisory. Application relevance is **needs review** because the deployed feature configuration is unavailable.
> Suggested update: `sample-client@4.0.1`. Compatibility checks: **not run**.

Versions and package names in that card are illustrative, not real upgrade guidance. Group related alerts by a resolving update, while preserving distinct advisories, affected versions, and occurrences. Show the difference between no matches and incomplete analysis.

Export an SBOM for inventory and VEX for scoped applicability assessments when needed. VEX is a statement about a product and vulnerability; it does not generate the supporting evidence. In particular, preserve an investigation state rather than turning missing evidence into not affected. [OpenVEX specification](https://github.com/openvex/spec/blob/main/OPENVEX-SPEC.md), [CycloneDX VEX](https://www.cyclonedx.org/use-cases/vulnerability-exploitability/).

**Reuse points identified before implementation.** Initial inspection found useful building blocks and concrete gaps. The MVP now adds the typed SCA artifact and `scanDependencies` entry point described in the implementation plan:

- The [static triage skill](../plugins/codex-security/skills/triage-finding/SKILL.md) already accepts advisory and scanner evidence. [Dependabot intake](../plugins/codex-security/skills/triage-finding/references/github-rest-intake.md) preserves package/version and fix information.
- The [triage contract](../plugins/codex-security/skills/triage-finding/references/triage-result-contract.md) is structured JSON, but package/version claims remain free text and it lacks typed component/advisory records. Add a separate typed component/match artifact rather than forcing an inventory into completed findings. Reuse `needs_review` for unresolved assessments. A `not_actionable` verdict must not automatically become VEX `not_affected`: a product-policy decision is not necessarily evidence that the advisory cannot affect the product.
- Existing [scan import](../sdk/typescript/README.md) can retain sufficiently complete canonical findings. It is not an arbitrary OSV JSON importer and explicitly performs no security analysis.
- The [finding extensions object](../plugins/codex-security/schemas/findings.schema.json) is a potential place for associated SCA metadata. Inspection suggests JSON storage preserves it, but that needs a real round-trip test. [SARIF](../plugins/codex-security/scripts/finalize_scan_contract.py) and [CSV](../plugins/codex-security/scripts/finalize_scan_contract.py) use fixed projections and need deliberate metadata mapping.
- At design time, no dedicated headless static-triage API was available. The existing [validate method](../sdk/typescript/src/api.ts) invokes the distinct validation workflow; it is not an interchangeable static SCA entry point.
- The existing [triage evaluations](../evals/triage-finding/README.md) can support applicability evaluation, with separate deterministic tests for inventory and adapters.

**Suggested implementation sequence.** These are proposed internal steps, not changes to the public CLI:

1. **Establish the baseline.** Select representative repositories and pin OSV-Scanner plus one independent comparator. Evaluate the current triage skill on a small adjudicated applicability set before changing prompts or building orchestration.
2. **Add a narrow adapter.** Start with OSV JSON and resolved lockfiles. Retain raw evidence and typed package/advisory occurrences. Verify direct/transitive cases, multiple package versions, aliases, and incomplete inputs. Use the existing import path only for valid canonical findings.
3. **Expose static assessment deliberately.** Wrap the existing skill with typed SCA inputs and its structured output, preserving `needs_review` as the unresolved state. Preserve evidence references and independent package-match facts. Compare with and without language-specific static evidence.
4. **Ship review and update workflows.** Add the result card, base/head comparison, and upgrade handoff. Verify actual resolved versions and normal project checks; leave reviewable diffs for developers.
5. **Expand from measured needs.** Add artifact/container inputs, SBOM/VEX exports, more language evidence, and advisory-driven reassessment. Add license or malicious-package workflows only with their own success criteria.

Go is a strong first applicability experiment because govulncheck provides a meaningful conventional baseline. JavaScript/TypeScript is a sensible parallel inventory and developer-experience pilot for this repository, but success there must not be described as equivalent function-level coverage. Choose the first shipping ecosystem based on actual user workloads after those measurements.

The proposed architecture should preserve scan isolation and existing runtime settings. If a later implementation changes worker launch configuration, verify discovery, reducer, and resumed workers at the child-process boundary as required by this repository. No new command, flag, or default is proposed in this note.
