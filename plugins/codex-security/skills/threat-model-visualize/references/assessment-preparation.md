# Assessment reconciliation

Use this optional pass when a source scatters the facts needed for the selected view or the user explicitly supplies supplemental findings. The builder accepts a single `--assessment` input. For multiple supplied artifacts, create a derived evidence document containing verbatim, labeled excerpts with their source identities, statuses and snapshot identifiers; point the builder to it while preserving the originals. Keep conflicting snapshots explicit rather than merging them into one asserted state. This optional reconciliation does not automatically ingest scans. Preserve each finding’s status and provenance; do not treat findings as threat-model hypotheses or hypotheses as validated findings. Read the supplied assessment, not application code. Bind each represented scenario's title, mechanism, priority, prerequisites, impact and controls to its own substantive row or section and verify its supporting quotations. Mark local IDs as local. Do not treat neighboring rows, table headers or a verified exact quote as proof of a different claim.

First reconcile the architecture and its ordinary relationships across the assessment's scope. Identify which identity, storage, external and operational relationships explain its threats. For each selected path, reconcile the actor or input, least required authority, meaningful handoffs and returns, enforcement owner, relevant deployment conditions and the difference between ordinary flow and an unproven exploit transition. Check each alternative source against its own relationships, prerequisites and controls; avoid carrying a union of unrelated branches into a selection. Keep necessary architecture visible; secondary facets can remain in inspection or the full assessment. Do not imply omitted actions are absent. Distinguish actors and phases, such as supplied input and its later consumption; a prior action alone does not trigger a later event. An authority gain and a later authorized action are separate; unknown ordering or acquisition remains unknown.

Reconcile consequential source-described safeguards and proposals into selectable controls at their actual operations, including supported non-blocking limits. Split controls with different owners or effects; do not invent a stop where its effect is unknown. Check each control's actual operation, source, route, direction and configuration. Distinguish enforcing owners from affected components: producer filtering and collector retention, for example, may have different owners. For a proposed effect, state the conditions required for it to work if implemented and what would remain, without asserting deployment. Distinguish an allowed request, a denied sensitive result and an unknown error response. The source determines whether a local actor, victim, recipient or service controls a path; do not infer extra authority to complete the picture.

This process normalizes existing evidence. It cannot verify code, deployment, effective permissions or exploitation; preserve those gaps and use a separate security workflow only if independently requested.
