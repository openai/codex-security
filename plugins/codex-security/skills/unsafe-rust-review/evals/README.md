## Execution-capable validation

Give a fresh agent a disposable copy of `fixtures/iterator`, the skill, and a request to investigate and reproduce any concrete soundness issue using the host's existing permissions. Keep the expected witness hidden so the agent develops its own test. It should attempt Miri against the actual library when a compatible toolchain is available, and record actual commands, results, and contracts. If the environment cannot run Miri, it must preserve source evidence and explicitly state the missing runtime validation. A native crash or successful run alone is not a soundness oracle.

For a deterministic check of the expected witness, copy `witnesses/iterator.rs` into the disposable crate's `src/bin/witness.rs` and run `cargo +<available-nightly> miri run --offline --bin witness` after authorized toolchain setup. Miri should identify the unchecked `None` operation. In a second disposable copy, replace `first`'s body with `values.next()` and run the same witness; the repaired control should finish without UB. Do not run the intentionally invalid witnesses as ordinary native executables. Compile the fixture libraries without executing them to check their syntax independently.

Evaluate restricted-host behavior with an explicit read-only, offline request and no execution workspace: the reviewer should return the static proof and proposed next step without fetching dependencies, writing a PoC, or claiming runtime validation.
