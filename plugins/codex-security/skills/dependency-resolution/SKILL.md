# Dependency Resolution

Resolve dependencies by actually invoking the repository's existing ecosystem-native package-manager graph or installed-tree command, or its documented native dependency-resolver library/API, in genuinely read-only mode. The model chooses and orchestrates the appropriate native tooling and interprets its actual output; it never substitutes its own dependency-graph reconstruction. This skill is useful on its own and does not require a security scan, an external service, or a cloud worker.

**Artifact recursion guard:** When the caller has already established that this is not an artifact scan, do not repeat its check. Otherwise, check `CODEX_SECURITY_DEPENDENCY_ARTIFACT_SCAN` inline in the first tool call that inspects resolver startup or invokes resolution, before that work; never make a separate tool call solely for this guard. If it is `1`, stop immediately. Do not reconstruct the scanned artifact's dependency graph, invoke another dependency skill, query a package service, or submit a scan.

## Check Yarn Startup Before Invocation

Before any Yarn command, including `--version`, or Yarn resolver API call, inspect executable selection and startup configuration as data without launching Yarn. Check the applicable `.yarnrc` and `.yarnrc.yml` files, including inherited parent/workspace configuration and any configured alternate rc filename. Do not print configuration secrets. If repository-controlled configuration declares Classic `yarn-path`, modern `yarnPath`, or plugins, or the invocation would load a repository executable, wrapper, preload, or `.pnp.cjs`, stop native Yarn resolution and report that executing repository-controlled code is required. Do not run the selected code to inspect or validate it.

Use only an already-installed host Yarn executable or resolver library whose code is independent of the checkout, whose version matches the requested graph, and whose startup cannot load repository-controlled code. If that cannot be established from local data, report the blocker. Corepack's offline/auto-pin flags and Yarn's offline/script flags do not prevent startup delegation or plugin execution. `YARN_IGNORE_PATH=1` alone does not prevent plugin loading; do not bypass configuration and silently substitute another Yarn version or graph. A native API is subject to the same restriction: do not import resolver modules or executable PnP files from the checkout. These checks precede the fast path below; reuse them within the same unchanged scope and configuration.

## Fast Path for Dependency Counts

When the caller only requests dependency counts or a depth histogram and the appropriate read-only, offline native resolver is known, invoke it immediately. Calculate exact shortest depths and eligible public-package counts directly from its selected nodes, edges, and source identities, excluding private, first-party, or workspace dependencies indicated by that output and ignoring extraneous nodes outside the selected graph without separate reconciliation. A clearly public resolver-emitted source, including a legitimate unusual public source, requires no additional mirror, archive, or integrity verification for this count. Return only the requested result or a concise actual blocker.

Use only the project's actual already-installed package manager and its existing effective installation; do not probe or invoke another package manager merely because it appears in these examples. Appropriate native graph commands include:

- npm: `npm ls --all --long --json --offline --silent`.
- pnpm: `COREPACK_ENABLE_AUTO_PIN=0 COREPACK_ENABLE_NETWORK=0 npm_config_offline=true pnpm list --recursive --depth Infinity --json --silent`, only when this installed version reads its existing graph offline without mutation.
- Yarn: after the startup checks above, use the installed version's read-only native graph command. Do not assume Classic's `list` command exists in modern Yarn.
- Bun: `bun why '*' --top`, whose selected package identities and immediate reverse dependency edges include development and optional dependencies.
- uv: do not treat `uv tree --offline --locked` as a read-only default. Checking lock freshness can execute build backends before rejecting a stale lock. `--no-build` blocks ordinary source builds, but [uv documents exceptions for first-party and editable packages](https://docs.astral.sh/uv/reference/cli/#uv-tree-no-build). If current-graph validation requires dynamic or legacy build metadata from the root, a workspace member, or an editable dependency, report that metadata requirement as a blocker without invoking the backend. Both `uv tree` and `uv pip tree` can initialize or update caches, so their offline and no-build flags do not satisfy this skill's no-write requirement. Use an existing native installed-tree reader that does not write only when that installation matches the requested graph; otherwise report the build-metadata or cache-write blocker. Use `--frozen` only for an explicitly requested frozen-lock snapshot, subject to the same no-write requirement; it does not establish lock freshness.
- Cargo: `cargo metadata --format-version 1 --locked --offline`.
- Go modules without vendoring: obtain the selected build list with `GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off go list -m -json -mod=readonly all` and requirement edges with `GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off go mod graph`. Preserve the project's workspace and vendoring mode. The requirement graph can include unselected versions; use the native selected build list for identities and versions, without counting every requirement vertex or reconstructing version selection yourself.

These are examples, not an ecosystem or tooling allowlist: use the equivalent genuinely read-only, offline, customer-native graph command or resolver API for pip-managed environments, Maven, Gradle, other package managers, and mixed-ecosystem repositories. Preserve the requested project and workspace scope; use recursive or workspace-wide variants only when that scope authorizes them. Never hydrate or download a package-manager shim, allow Corepack to pin or edit `package.json`, run installation/build/lifecycle code, omit development/build/test, installed optional, peer, or workspace dependency graphs, or treat a command as safe when its actual version or project configuration writes files or accesses the network.

For npm, dependency-edge keys are installation names and may be aliases. Default JSON can omit the actual package name; obtain it from native detailed output such as `--long`, the native resolver API, or installed package metadata. Use an edge key as the package name only when established to be a non-alias. If the actual identity remains unknown, return a concise blocker rather than treating the alias as a package name.

Mechanically calculate shortest depths from the complete native graph: the first-party project root is depth zero and its direct public dependencies are depth one. Use each package's actual identity and selected version. Deduplicate only by ecosystem, normalized established public registry/source, package name, and selected version; retain the shortest actual depth for every identity, and traverse every emitted occurrence and its children even when that identity was previously seen. Exclude explicitly extraneous nodes, absent optional dependencies, versionless placeholders, and explicitly private or first-party/workspace package identities without discarding legitimate installed development, optional, peer, bundled, or alternate-public-source packages; traverse authorized workspace/project roots and genuine remaining child edges. Do not filter on integrity metadata, registry-domain assumptions, or unavailable child `name` properties. Return `{"depthCounts":[...]}` with index zero representing depth one, retaining zero-count intermediate depths.

After any required Yarn startup checks, do not run separate Git-revision or snapshot checks, manifest or lockfile inventories, resolver-availability checks, installation audits, extraneous-installed-package reconciliation, integrity or provenance checks, registry-configuration or mirror inspections, advisory checks, or other preliminary investigation. Inspect additional local evidence only when the native output cannot establish the requested complete effective graph. If public eligibility remains genuinely ambiguous in a way that changes the requested count, return a concise blocker instead of conducting a broader source, mirror, or integrity audit. Defer any full source or integrity verification needed for actual scan submission to that later workflow. Briefly narrate genuine resolution progress when the host surfaces task activity, without introducing extra checks or delaying the result.

## Establish the Requested Scope

- For a repository-wide request, resolve the dependency graphs of its relevant projects and workspaces without requiring a Git diff.
- For a project- or path-scoped request, inspect the root, parent, project, and workspace manifests or lockfiles needed to explain that project's graph. These files are supporting dependency context even when an ordinary source-review inventory excludes them; they do not authorize reviewing unrelated first-party source.
- For a PR, commit, branch comparison, or working-tree request, reuse the exact requested base, head, and diff mode. Read committed manifests and locks from their respective Git revisions. For a working-tree request, compare the requested base with both staged and unstaged changes; account for relevant new files without staging or modifying them. Do not substitute another revision, silently widen the diff, or infer a package change from an unrelated edit.
- When another skill supplies an existing scan, project, file partition, or authorization boundary, preserve it. This skill does not start, finalize, or replace a scan.

## Reconstruct the Effective Graph

When the appropriate read-only native resolver is known, run it immediately; inspect the package and build systems only when needed to identify or operate it. Use Bash to run the existing package-manager dependency-resolution or installed-tree command, or a read-only local script that invokes the package manager's documented native resolver library/API. Obtain the complete effective graph from that real resolver's output, with the same selected versions, hoisting, dependency aliases, optional and peer dependencies, workspace relationships, platform selection, lock behavior, and installation policy the customer actually uses. Local scripts may normalize, deduplicate, or calculate shortest depths from resolver-emitted nodes and edges; they must not replace the resolver with generic or hand-written lockfile parsing, an ad hoc graph traversal of inferred relationships, or model-generated resolution. Never mentally infer, approximate, or guess package versions, graph edges, dependency chains, or counts.

Follow the native resolver's actual installed nodes and edges. An optional dependency, including an optional peer dependency, that the native resolver confirms is not installed is absent, not an unresolved required dependency; do not invent its node or treat its absence as a resolution failure.

Use committed lock state, project and workspace manifests, hidden or ignored installed lockfiles, existing installed package metadata, lock shards, and build configuration only when the genuine native resolver requires them or its output leaves the requested snapshot or effective installation materially ambiguous. Do not inventory or validate those inputs separately when native output already establishes the requested graph. An installed tree establishes the requested versions only when it represents the selected effective installation; never substitute current installed state for another Git revision or mismatched dependency-manifest, lockfile, workspace, or installation-policy state. Unrelated working-tree source changes do not invalidate an otherwise matching installed dependency graph. For the same selected dependency snapshot, a calculation and subsequent scan must use the same actual installed or locked customer-native resolver output; never replace an already selected package version with a newer registry version that merely satisfies its manifest range. Explain project-local dependencies in the context of the actual shared root or workspace graph. Work across whichever JavaScript, Python, Rust, Go, JVM, .NET, Ruby, PHP, Swift, Bazel, or other ecosystems the repository uses; examples are not an allowlist.

Resolve:

- The first-party project or workspace using each package, its actual selected version, and its direct or transitive dependency chains.
- Dependencies relevant to production, development, optional features, peers, build and test tooling, platforms, installers, or generated/distributed application code when the requested scope makes them relevant.
- Registry and source configuration, scoped overrides, mirrors, direct public archives, public Git references, alternate public package repositories, local paths, workspace links, and private sources.
- The effective installation policy, including trusted or frozen lock behavior, version constraints, release-age or cooldown rules, and relevant CI or container configuration. Distinguish the version that would actually install from an apparent version excluded by policy. If a locked installation would fail, say so instead of inventing a fallback.
- For a Git diff, the before-and-after graph, actual package additions and version changes, removed packages, changed first-party usage, and newly introduced unlocked installers, floating executables, or unpinned workflow actions. Preserve exact evidence locations and distinguish an unsafe installation control from an intentional package update.

When necessary, inspect relevant first-party usage only within the caller's authorized source scope. Do not treat a package's directness or lockfile membership alone as proof that its code executes in the application.

Use known genuinely read-only native tooling; do not run invocations that install packages, modify lockfiles, run package lifecycle or installation scripts, execute repository application code or arbitrary dependency code beyond the trusted package-manager resolver itself, mutate installed state, or write or delete repository files, package-manager caches, or logs. Do not make a separate tool call to audit an already-known read-only invocation. Offline flags or read-oriented command names alone do not establish that a package-manager CLI is nonmutating; use its documented read-only native resolver API instead when the CLI performs ancillary writes.

For an ordinary dependency scan, preserve existing permission to use authorized, read-only public registry or package metadata queries only when required by the genuine native resolver for the requested effective graph and after the package and source have been established as public; never select registry versions independently of that resolver or override the version selected by the native installation or lock state. When the caller explicitly requires offline calculation, that stricter caller requirement overrides this general registry-query permission: use only a genuinely offline, read-only native resolver against exact existing local state, without contacting registries or network services, fetching remote metadata, or downloading packages. Never send private package names, internal endpoints, repository details, credentials, or ambiguous sources to an unrelated service; do not require a third-party dependency-graph service or a cloud worker. Leave vulnerability-database and advisory lookups to the caller's advisory-checking workflow.

If the required ecosystem-native tooling is unavailable, cannot run without mutation, or cannot establish the exact requested snapshot's customer-effective package versions, real dependency edges, or installation behavior, report the concrete blocker directly or through the caller's existing coverage-limitation surface when one is available. Do not fall back to model-based resolution, a hand-written graph reconstruction, stale installed state, an unrelated revision, guessed versions, fabricated dependency chains, or an invented limit.

## Separate Public Identity from First-Party Context

Classify packages as publicly retrievable, private, workspace-local, first-party, or ambiguous using the native resolver's emitted source identity and, only when the requested operation requires it, additional actual lockfile or source evidence. Preserve public nonstandard Git, direct-archive, or alternate-registry sources accurately; do not misclassify them merely because they are not hosted by a default registry. Conversely, do not reinterpret an internal registry, authenticated source, workspace package, or local archive as public. Treat an internal mirror as the corresponding public package only when repository configuration and the recorded package or artifact evidence actually establish that equivalence.

When the caller expressly requests a source or provenance explanation, or native resolver output leaves public eligibility ambiguous in a way that changes the requested result, inspect only the effective project, user, global, system, or scoped registry configuration needed to resolve that ambiguity, locally and without printing raw settings, credentials, or private hostnames. When a configured public-registry mirror matches the resolver's exact package, version, and archive, with strong recorded installed-tree or lockfile integrity, normalize it to the corresponding public package identity; do not hardcode default registry domains or require a committed lockfile. Never treat an explicitly private or alternate-scoped source, an unknown origin, or a mirror whose public equivalence cannot be established as public.

When the native resolver confirms that an installed package is bundled or vendored inside another installed artifact, inherit its source and public eligibility from that actual containing artifact. A bundled child's missing individual registry URL or integrity value is not evidence that it is private, unresolved, or ineligible. Its containing artifact must itself be established as public, including a customer mirror proven equivalent to the public source; never assume that an unknown or private artifact or an unverified mirror is public.

Keep first-party paths, project names, dependency chains, source excerpts, internal hostnames, account information, package-manager configuration, tokens, and credentials local. Never disclose credential values in tool output or artifacts. This skill never submits first-party or private context, starts a cloud job, or transmits more than the verified-public package or source identity needed for an authorized read-only metadata query. If a parent workflow later sends public package identities elsewhere, provide only the public fields its existing contract explicitly supports; when a public source cannot be faithfully represented, describe the limitation rather than dropping provenance or inventing another field.

## Return the Result Appropriate to the Caller

For standalone use, give a concise evidence-backed answer suited to the request: the relevant projects, direct and transitive packages, selected versions, public/private classification, meaningful dependency chains, effective installation controls, requested before-and-after changes, and concrete unresolved questions. Do not require a specific file, JSON schema, security report, or artifact directory.

When invoked by an existing dependency scan, preserve the parent's exact Git diff or requested complete current repository graph and, only when requested, populate its existing local `dependency-discovery.json` with the same `baseRevision`, `headRevision`, `mode`, `changedFiles`, `dependencies`, `unsafeInstallations`, and `coverageLimitations` structure. For a complete current graph, use `baseRevision: null`, the actual current Git revision or `null` as `headRevision`, `mode: "repository"`, and `changedFiles: []`; record every current selected public direct or transitive package with `oldVersion: null` and its actual locked `newVersion`. Never manufacture a parent-commit diff, empty-tree comparison, or changed lockfile to represent the current graph. Preserve the existing changed-file (`path`, `status`, `kind`, `patch`), unsafe-installation (`path`, `startLine`, `command`, `kind`), and limitation (`path`, `package`, `reason`) shapes. Reuse the existing public dependency identity (`ecosystem`, `registry`, `package`, `oldVersion`, `newVersion`) and existing local evidence fields `anchorPath`, `anchorStartLine`, and `dependencyTypes`. Record private or unresolved sources only as existing local limitations; do not invent output properties or expose private source details. Leave `dependency-impacts.json`, scan submission, cloud acquisition, security finding creation, reporting, and finalization to the calling workflow.

When invoked by another analysis or advisory-checking skill, return the local resolved graph and first-party context it requested. The caller owns its own findings, advisory lookup, and reporting; dependency resolution must not perform those operations itself.
