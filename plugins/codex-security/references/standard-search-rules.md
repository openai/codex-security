# Standard search rules

Inspect representative source before choosing rules. Look for the framework's actual entry points, authorization checks, sensitive operations, data formats and credential-bearing files. For each exposed boundary, choose patterns that identify its implementations throughout the authorized tree. Prefer concrete symbols, annotations and path conventions over broad language or directory names. Check representative matches and misses while drafting. A match earns a file a review. It is not evidence of a vulnerability.

Save the rules as a JSON array in `<scan_dir>/artifacts/01_context/standard-rules.json`. Each rule has a `path` or `content` JavaScript regular expression, or both. Both must match when present. Paths are repository-relative with forward slashes. Content patterns are multiline and case-sensitive. For example, `{"path":"[.]ts$","content":"registerWebhook\\("}` selects TypeScript files that call that registration function. Use the repository's own names.

Run the bundled helper from `<plugin_dir>/scripts/launch_codex_security_mcp --helper standard-queue` (use the `.cmd` launcher on Windows). Quote each argument for the current shell.

- `build <scan_dir> <repo_root> <registered scope paths...>` runs all rules once and saves sorted unique matches in numbered batches of up to five. Use the registered target-paths file when supplied (the helper reads it directly), otherwise pass the exact registered scopes, using `.` only for a whole repository. Explicitly requested files always enter the queue. Resume an existing queue instead of rebuilding it.
- `pending <scan_dir> <after_batch_id> <count>` lists up to that many unfinished batches after the given ID. Start at zero. Fill available independent worker slots and remember active batch IDs so two workers never get the same assignment. Pass the exact file list and the investigator brief. Reuse idle workers with fresh assignments. Keep declined or partially read files pending.
- Give each assignment a separate JSON output file under the scan's artifacts directory. Have the investigator save its full structured return there. As the parent, run `reviewed <scan_dir> <batch_id>` serially with that JSON on standard input. This saves the original findings and counterevidence in the same update that marks files reviewed. If the worker can only return a message, pass its full JSON unchanged. If the return is unreadable, retry the unfinished batch.
- Run `check <scan_dir>` to confirm all files were reviewed. Return to batch zero to pick up unfinished files after a partial review or restart.

## Validate the returned candidates

Use the supplied Python interpreter to run `<plugin_dir>/scripts/standard_validation.py pending <scan_dir> [after_cursor]`. It returns up to five undecided candidates with their stable IDs and original evidence. Start at zero. Use the last returned cursor for the next assignment. Restart at zero after an interruption or when checking for completion.

Have each reviewer return a JSON array with one row per assigned ID. Each row has a `candidateId` and a `parts` array in claim order. Each part names its `disposition` (`reportable`, `duplicate`, `rejected`, `not_applicable`, or `deferred`) and its source-backed `reason`, including the specific gap for a deferral. Return independent claims separately. Claim IDs are the supplied ID plus the one-based part number, such as `standard-4.2`. A duplicate also needs `duplicateOf` naming a reportable claim with the same broken control and fix. Give the parent the details it needs to publish the findings.

As each reviewer finishes, pass its unchanged JSON on standard input to `standard_validation.py record <scan_dir>`. Run these updates serially. Checkpoint the batch through the bound draft tool with `complete: false`, or update the SDK files when using its file handoff. For a reportable claim put its claim ID in `finding.provenance.candidateId`. If one finding covers other independently accepted claims with the same fix, list their claim IDs in `provenance.duplicateCandidateIds`. For a rejection or inapplicable claim, record the claim ID as `candidateId` on a `rejected` or `not_applicable` surface with the reason in `notes`. Put each deferred claim ID and its proof gap in `reviewState.deferred`. On resume, restore any unpublished decisions from `artifacts/04_validation/standard-decisions.json`.

When all assigned batches have returned, read from cursor zero again. Submit a complete draft only when that page is empty. A caller-supplied custom validation workflow owns its own decisions.
