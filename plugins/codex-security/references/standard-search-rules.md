# Standard search rules

Inspect representative source before choosing rules. Look for the framework's actual entry points, authorization checks, sensitive operations, data formats and credential-bearing files. Consider ownership and authorization at object access, injection at interpreters, path traversal and request forgery at file and network boundaries, and parser or resource exhaustion risks. For each exposed boundary, choose patterns that identify its implementations throughout the authorized tree. Prefer concrete symbols, annotations and path conventions over broad language or directory names. Check representative matches and misses while drafting. A match earns a file a review. It is not evidence of a vulnerability.

When the caller requests batching in context, apply the rules with an offline search tool over the supplied scope, dispatch the matching files in batches, and validate the returned candidates in batches using the caller’s draft handoff. Skip the file and helper instructions below for that handoff.

Save the rules as a JSON array in `<scan_dir>/artifacts/01_context/standard-rules.json`. Each rule has a `path` or `content` JavaScript regular expression, or both. Both must match when present. Paths are repository-relative with forward slashes. Content patterns are multiline and case-sensitive. The helper decodes UTF-8 and BOM-marked UTF-16 text. For text over 8 MiB, it queues the file if the rule’s path filter permits it, since a JavaScript expression can span the whole file. Binary files can enter through an explicit file selection or a path-only rule. For example, `{"path":"[.]ts$","content":"registerWebhook\\("}` selects TypeScript files that call that registration function. Use the repository's own names.

Run the bundled helper from `<plugin_dir>/scripts/launch_codex_security_mcp --helper standard-queue` (use the `.cmd` launcher on Windows). Quote each argument for the current shell.

- `build <scan_dir> <repo_root> <registered scope paths...>` runs all rules once and saves sorted unique matches in numbered batches of up to five. Use the registered target-paths file when supplied (the helper reads it directly), otherwise pass the exact registered scopes, using `.` only for a whole repository. Explicitly requested files always enter the queue. Resume an existing queue instead of rebuilding it.
- `pending <scan_dir> <after_batch_id> <count>` lists up to that many unfinished batches after the given ID. Start at zero. Fill available independent worker slots and remember active batch IDs so two workers never get the same assignment. Pass the exact file list and the investigator brief. Reuse idle workers with fresh assignments. Keep declined or partially read files pending.
- Ask each investigator to return its full JSON to the parent. A worker with an explicitly writable output file may return it there. As the parent, pass the full JSON unchanged on standard input to `reviewed <scan_dir> <batch_id>`. The saved return preserves supporting-file evidence. Only fully reviewed members of this assignment advance its queue. If the return is unreadable, retry the unfinished batch.
- Run `check <scan_dir>` to confirm all files were reviewed. Return to batch zero to pick up unfinished files after a partial review or restart.

## Validate the returned candidates

Use the supplied Python interpreter to run `<plugin_dir>/scripts/standard_validation.py pending <scan_dir> [after_cursor]`. It returns up to five undecided candidates with their stable IDs and original evidence. Start at zero. Use the last returned cursor for the next assignment. Restart at zero after an interruption or when checking for completion.

Have each reviewer return a JSON array with one row per assigned ID. Each row has a `candidateId` and a `parts` array in claim order. Each part names its `disposition` (`reportable`, `duplicate`, `rejected`, `not_applicable`, or `deferred`) and its source-backed `reason`, including the specific gap for a deferral. Return independent claims separately. Claim IDs are the supplied ID plus the one-based part number, such as `standard-4.2`. A duplicate also needs `duplicateOf` naming a reportable claim with the same broken control and fix. Give the parent the details it needs to publish the findings.

As each reviewer finishes, pass its unchanged JSON on standard input to `standard_validation.py record <scan_dir>`. Run these updates serially. Checkpoint the batch through the bound draft tool with `complete: false`, or update the SDK files when using its file handoff. For a reportable claim put its claim ID in `finding.provenance.candidateId`. If one finding covers other independently accepted claims with the same fix, list their claim IDs in `provenance.duplicateCandidateIds`. For a rejection or inapplicable claim, record the claim ID as `candidateId` on a `rejected` or `not_applicable` surface with the reason in `notes`. Put each deferred claim ID and its proof gap in `reviewState.deferred`. On resume, restore any unpublished decisions from `artifacts/04_validation/standard-decisions.json`.

When all assigned batches have returned, read from cursor zero again. Ordinarily, submit a complete draft when that page is empty and every file was reviewed. A caller-supplied custom validation workflow owns its own decisions.

At the original registered SDK investigation deadline, stop dispatching new work. Include each unread queue path in `reviewState.deferred[].paths` with its reason. For a returned candidate that still lacks a validation decision, add a deferred row with its original `candidateId`, a concrete proof gap and the relevant paths. The workbench preserves the acknowledged candidate and counterevidence in that row. Reconcile every existing decision normally. Submit the terminal draft with the verified findings and explicit unfinished coverage. A separate custom-validation pass still owns the provisional candidates and their dispositions. If the local queue has no saved caller allowance and start time, keep unfinished work in a resumable checkpoint.
